# Periodica App — Kivy / KivyMD desktop GUI

The desktop GUI (Windows, macOS, Linux) for the `periodica` scientific library,
published as `pip install periodica-app`. **Android and iOS are not targets.**
They were dropped on 2026-10-02, together with the buildozer/APK tooling.

## Architecture

- **src layout:** all source lives in `src/periodica_app/`.
- **The science lives in `periodica`:** data, registries, `periodica.layout_math`
  positions and calculators. Never duplicate physics or data logic here; this
  repo holds presentation only.
- **Shell:** `app.py` defines `PeriodicaApp(MDApp)`, a navigation panel plus a
  `ScreenManager`. `DOMAINS` lists the 12 domains. A domain is enabled once a
  factory is registered with `register_screen(key, factory)`; factories run
  lazily on first navigation. Only **quarks** is live today.
- **Screens** (`screens/`):
  - `base_screen.DomainScreen`: a data-driven 2-D domain tab with a toolbar,
    `ControlDrawer`, `CanvasView` and `InfoSheet`. A subclass supplies only
    config: layout modes → renderers, properties, toggles, display config and
    an optional enriching `data_loader`.
  - `quarks_screen.py`: the template domain (config + enriching loader).
- **Widgets** (`widgets/`): `CanvasView` (2-D canvas with pan, zoom and tap;
  drawing is delegated to a renderer), `ControlDrawer` (controls built from a
  config dict), `InfoSheet` (selected-item details from a display config).
- **Renderers** (`renderers/`): `BaseRenderer` subclasses that take positions
  from `periodica.layout_math` and draw with Kivy canvas instructions.
- **Planned (master plan, Phase 6):** a GPU volume renderer for orbitals and
  molecules, using GLSL ES 1.00 shaders generated by the Rust library and run
  through Kivy `RenderContext`/`Fbo`. See `docs/dev/gl-spike.md` for what the
  Kivy GL stack can and cannot do.

## Commands

```bash
pip install -e ".[dev]"            # editable install + pytest, ruff, pyinstaller
python -m periodica_app            # run the app (or: periodica-app)

build.bat        | ./build.sh      # ruff + tier-A tests (headless)
build.bat gpu    | ./build.sh gpu  # ... + tier-B GPU tests
build.bat exe    | ./build.sh exe  # ... + PyInstaller build -> dist/PeriodicaApp/

python tools/gl_spike.py --matrix  # GL capability spike (docs/dev/gl-spike.md)
```

If another checkout is installed editable (for example in a worktree), run with
`PYTHONPATH=src` so this checkout's package shadows it. The build scripts do
this for you. Verify with `python -c "import periodica_app; print(periodica_app.__file__)"`.

## Tests

| Tier | Selection | What it may do |
|---|---|---|
| A | default (`pytest tests`) | Pure logic, controllers, module imports. **Must not create a window.** `tests/conftest.py` makes `import kivy.core.window` raise during tier-A runs. |
| B | `@pytest.mark.gpu`, run with `pytest -m gpu` | Needs a GL context. Uses the hidden-window `gl_window` fixture. Skipped unless selected. |
| C | library CI | `glslangValidator` on every generated shader variant (not in this repo yet). |

## Conventions

- Library code (`from periodica…`) does all computation. Kivy-dependent code
  stays here.
- **Keep window-creating imports lazy.** `kivy.core.window`, and anything that
  imports it at module level (`kivy.uix.spinner`/`dropdown`, `kivymd`), goes
  inside the function that needs it. Otherwise headless tier-A tests cannot
  import the module.
- kv rules instantiate custom widgets by class name. A Widget subclass is
  registered with the Factory when its module is imported, so keep those
  imports even though linters call them unused (`# noqa: F401` + comment).
- Domain screens are config, not code. Add a domain by writing a config module
  plus renderers, then `register_screen` it.
- GL code: GLSL ES 1.00 only. Use `precision highp float;` under
  `#ifdef GL_ES`. Pass uniforms as Python floats. Call `fbo.ask_update()`
  before `fbo.draw()` when nothing changed. Full list of rules in
  `docs/dev/gl-spike.md`.
- Lint: `ruff check src tests tools` must be clean (config in `pyproject.toml`).

## Project Philosophy & Senior Development Standards

These reflect senior-level software engineering discipline: clarity,
maintainability, extensibility, automation, and long-term sustainability.

### 1. Core Architectural Principles (SOLID + Beyond)

Apply SOLID principles rigorously:
- **Single Responsibility:** each class / module has one clear reason to change.
- **Open / Closed:** entities are open for extension but closed for modification.
- **Liskov Substitution:** subtypes must be fully substitutable for base types.
- **Interface Segregation:** prefer small, client-specific interfaces over large ones.
- **Dependency Inversion:** depend on abstractions, not concretions.

**DRY + Strategic Generalization:** aggressively eliminate duplication. When
similar logic appears across modules or projects, extract it into well-designed
base classes, abstract base classes, or shared libraries using proper
inheritance and composition. Favor composition over inheritance when behaviour
is likely to vary.

**Separation of Concerns:** keep UI, business logic, data access, and
configuration strictly separated.

### 2. Python-Specific Standards

- **UI Layer:** every Python project with a graphical interface must use
  KivyMD (Material Design for Kivy) for consistency, modern look, and
  cross-platform capability.
- **Build & Distribution:**
  - Every Python project must include a `build.bat` (Windows) and an
    equivalent shell script for other platforms.
  - The build must produce a single executable (via PyInstaller or equivalent).
  - Target ≥ 90 % code coverage on unit + integration tests before producing
    the final EXE.
  - Include automated linting (ruff / black), type checking (mypy or pyright),
    and tests as part of the build pipeline.

### 3. Documentation Standards

- Every project must maintain up-to-date HTML documentation focused on
  "How To" basics (setup, common tasks, architecture overview, key workflows).
- Keep the documentation in the repository root or `/docs` folder and
  version-controlled.

### 4. Additional Senior Engineering Practices

**Code Quality & Maintainability:**
- Clear, self-documenting code with meaningful names.
- Comprehensive but focused unit and integration tests.
- Logging and error handling that aids debugging without verbosity.
- Consistent naming conventions and project structure across repositories.

**Automation First:**
- Automate builds, tests, packaging, and documentation generation.
- Minimise manual steps required to go from clone → run → deploy.

**Security & Performance Awareness:**
- Validate inputs, handle secrets securely, and be mindful of resource usage.
- Profile critical paths and optimise when necessary.
